# Triage

把项目 issue tracker 上的 issue 推进一套小型 triage 角色状态机。

若本仓库把外部 pull request 也当作请求面（见 issue-tracker 配置），matt-triage 同样覆盖它们：**PR 是带附件代码的 issue**，同一套角色、状态与状态机，下文标 "for a PR" 处有少量差异。裸 `#42` 按 tracker 配置解析为 issue 或 PR。

matt-triage 期间发到 issue tracker 的每条评论或 issue **必须**以此免责声明开头：

```
> *This was generated by AI during triage.*
```

## 角色

两个 **category** 角色：

- `bug`：东西坏了
- `enhancement`：新功能或改进

五个 **state** 角色：

- `needs-triage`：维护者需要评估
- `needs-info`：等待报告者补充信息
- `ready-for-agent`：已充分规格化，可供 AFK agent 领取
- `ready-for-human`：需要人类实现
- `wontfix`：不会处理

对 PR，同一状态对照已附代码解读：`ready-for-agent` 表示已附 brief，agent 应对 diff 采取下一步；`ready-for-human` 表示可供人类 merge。

每个已 triage 的 issue 应恰好带一个 category 与一个 state。若 state 冲突，先标出并询问维护者，再做其他事。

以上是规范角色名。issue tracker 上的实际标签字符串可能不同。映射应由配置提供。若缺失，请用户先运行 `matt-configure-project-docs`。

状态迁移：未打标 issue 通常先到 `needs-triage`；再从此到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。`needs-info` 在报告者回复后回到 `needs-triage`。维护者可随时覆盖；看起来异常的迁移先标出并询问再继续。

## 调用方式

维护者调用 `matt-triage` 并用自然语言说明想做什么。解读请求并行动。示例：

- "Show me anything that needs my attention"
- "Let's look at #42"（issue 或 PR）
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## 展示需要关注的事项

查询 issue tracker，按最旧优先呈现三个桶：

1. **Unlabeled**：从未 triage。
2. **`needs-triage`**：评估进行中。
3. **`needs-info` 且自上次 matt-triage notes 后报告者有活动**：需要再评估。

当 PR 在范围内时，把外部 PR 纳入这些桶，并给每行打 `[PR]` 或 `[issue]`。发现面只含*外部* PR（tracker 配置定义谁算外部），协作者进行中的 PR 不是 matt-triage工作。该过滤仅用于发现；显式点名的 PR 无论作者一律 triage。

展示计数与每条一行摘要。让维护者挑选。

## Triage 具体 issue 或 PR

1. **收集上下文。** 读完整 issue/PR（正文、评论、标签、作者、日期；对 PR 还要读 diff）。解析既有 matt-triage notes，避免重问已解决的问题。用项目 domain glossary 探索代码库，遵守相关 ADR。对代码库做两项检查：(a) **冗余**：按领域概念（不只请求措辞）搜索是否已有实现，并报告搜索位置。若已有，则为 already-implemented `wontfix`（步骤 5）。(b) **既往拒绝**：读 `.out-of-scope/*.md`，呈现任何相似请求。

2. **推荐。** 告诉维护者你的 category 与 state 建议及理由，加上与请求相关的代码库摘要（含是否已实现）。等待指示。

3. **核实主张。** 在任何 matt-grilling 之前，确认主张站得住。对 bug：按报告者步骤复现。对 PR：确认 diff 做了它声称的事（checkout、跑相关测试或命令）。报告结果：confirmed（含代码路径）、failed、或信息不足（强烈 `needs-info` 信号）。核实确认会让 agent brief 强很多。

4. **Grill（若需要）。** 若请求需要充实，同时采用 **matt-grilling** 与 **matt-domain-modeling** 纪律，一轮问题一轮地 grill 成形，锐化领域术语，决策落地时同步更新 `CONTEXT.md`/ADR。

5. **落实结果：**
   - `ready-for-agent`：发一条 agent brief 评论（见 AGENT-BRIEF）。
   - `ready-for-human`：结构同 agent brief，但说明为何不能委托（判断调用、外部访问、设计决策、手工测试）。
   - `needs-info`：发 matt-triage notes（下方模板）。
   - `wontfix`：关闭 issue，评论视*原因*而定：
     - **Already implemented**：变更已在代码库。指向所在位置；**不要**写入 `.out-of-scope/`（该 KB 只记*被拒*请求，不记已建成的）。
     - **Rejected (bug)**：礼貌说明后关闭。
     - **Rejected (enhancement)**：写入 `.out-of-scope/`，评论中链接，再关闭（见 OUT-OF-SCOPE）。
   - `needs-triage`：打上角色。若有部分进展可可选评论。

## 快速状态覆盖

若维护者说 "move #42 to ready-for-agent"，信任并直接打角色。先确认你将做什么（角色变更、评论、关闭），再行动。跳过 matt-grilling。若未经过 matt-grilling 会话就移到 `ready-for-agent`，询问是否要写 agent brief。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

matt-grilling 中已解决的全部收进 "established so far"，避免丢失。问题必须具体可执行，不要写 "please provide more info"。

## 恢复先前会话

若 issue/PR 上已有 matt-triage notes，先读它们，检查报告者是否回答了未决问题，再呈现更新后的图景再继续。不要重问已解决的问题。
