# Diagnosing Bugs

难缠 bug 的纪律。只有在明确说明理由时才可跳过阶段。

探索代码库时，若存在 `CONTEXT.md` 则先阅读，建立相关 module 的清晰心智模型，并检查你所触及区域的 ADR。

## 脱敏（Redact）

本技能会要求展示命令、输出与捕获的产物。**先脱敏每一个密钥**：用 `<REDACTED>` 替换。把循环建立在环境变量之上，使凭证留在环境中，而不是出现在你展示的内容里。捕获的产物可能带有 auth headers：只引用承载信号的那些行。

若脱敏后的输出不足以诊断，明确说明并向用户索取所需信息。

## Phase 1: 建立反馈循环

**这就是本技能的核心。** 其余都是机械步骤。只要你有一个**紧**的、针对*这个* bug 会变 red 的 pass/fail 信号，你就会找到原因；二分、假设检验与埋点都只是消费它。若没有，再怎么盯着代码也救不了你。

在此投入不成比例的精力。**要进取。要有创造力。拒绝放弃。**

### 构造反馈循环的方式（大致按此顺序）

1. **失败测试**：落在能触及该 bug 的任意 seam（unit、integration、e2e）。
2. **Curl / HTTP 脚本**：对着运行中的 dev server。
3. **CLI 调用**：用 fixture 输入，把 stdout 与已知正确的 snapshot 做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）：驱动 UI，并对 DOM / console / network 断言。
5. **重放捕获的 trace**：把真实网络请求 / payload / 事件日志存盘，在隔离中重放代码路径。
6. **一次性 harness**：拉起系统的最小子集（一个服务、mock 依赖），用单次函数调用走到 bug 路径。
7. **Property / fuzz 循环**：若 bug 是「有时输出错误」，跑 1000 个随机输入并寻找失败模式。
8. **二分 harness**：若 bug 出现在两个已知状态之间（commit、数据集、版本），自动化「在状态 X 启动、检查、重复」，以便 `git bisect run`。
9. **差分循环**：同一输入跑旧版 vs 新版（或两套配置），diff 输出。
10. **HITL（human-in-the-loop）清单**：最后手段。若必须有人点击，用下方「可选 HITL 清单」驱动对方，使循环仍有结构。捕获的输出反馈给你。（可选：仓库中的 `./scripts/hitl-loop.template.sh` 是同类结构的 bash 模板，任何能跑 shell 的 Agent 都可用，并非某一产品专属。）

建对反馈循环，bug 就修了九成。

### 收紧循环

把循环当产品对待。一旦有了*某个*循环，就去**收紧**：

- 能更快吗？（缓存 setup、跳过无关初始化、收窄测试范围。）
- 信号能更锐吗？（断言具体症状，而不是「没崩」。）
- 能更确定吗？（钉死时间、固定 RNG seed、隔离文件系统、冻结网络。）

一个 30 秒且 flaky 的循环几乎不比没有循环好；一个 2 秒且确定的循环才是紧的，才是调试超能力。

### 非确定性 bug

目标不是干净复现，而是**更高的复现率**。把触发器循环 100 次、并行、加压、收窄时间窗口、注入 sleep。50% flake 可调试；1% 不行，所以持续抬高复现率直到可调试。

### 当真建不出循环时

停下来，明确说明。列出你试过什么。向用户索取：(a) 能复现的环境访问权，(b) 已脱敏的捕获产物（HAR、日志 dump、core dump、带时间戳的录屏），或 (c) 在生产临时加埋点的许可。**没有循环就不要进入假设。**

### 完成标准：一个会变 red 的紧循环

Phase 1 完成的条件是循环**紧**且**具备变 red 的能力**：你能点名**一条命令**（脚本路径、测试调用、curl），且你**已经至少跑过一次**（展示调用与输出，已脱敏），并且它：

- [ ] **Red-capable**：驱动实际 bug 代码路径，并断言**用户的确切症状**，因而能对这个 bug 变 red、修好后变 green。不是「跑完没报错」；它必须能*抓住这个具体 bug*。
- [ ] **Deterministic**：每次跑出相同 verdict（flaky bug：按上文钉到足够高的复现率）。
- [ ] **Fast**：以秒计，不以分钟计。
- [ ] **Agent-runnable**：可无人值守运行；人只通过 HITL 清单（或可选 `./scripts/hitl-loop.template.sh`）介入。

若你发现自己在这条命令存在之前就读代码建理论，**停下：直接跳到假设，正是本技能要防止的失败。** 没有 red-capable 命令，就没有 Phase 2。

## Phase 2: 复现 + 最小化

跑循环。看着它因 bug 出现而变 red。

确认：

- [ ] 循环产生的是**用户**描述的失败模式，而不是碰巧附近的另一种失败。错 bug = 错修复。
- [ ] 失败可跨多次运行复现（或对非确定性 bug，复现率高到足以对着调试）。
- [ ] 你已捕获确切症状（错误信息、错误输出、缓慢时机），以便后续阶段验证修复真正对准它。

### 最小化

一旦变 red，把复现缩到**仍会变 red 的最小场景**。一次切掉一个输入、调用方、配置、数据或步骤，每次切开后重跑循环，只保留对失败仍有负载的部分。

为什么：最小复现会缩小 Phase 3 的假设空间（更少可疑的活动部件），并在 Phase 5 成为干净的回归测试。

完成条件：**每一个剩余元素都是负载性的**：去掉任何一个都会让循环变 green。

在尚未复现**且**最小化之前，不要继续。

## Phase 3: 提出假设

在测试任何一个之前，先生成 **3–5 个排序过的假设**。只生成单一假设会锚定在第一个看起来像的想法上。

每个假设必须**可证伪**：写出它的预测。

> 格式：「若 <X> 是原因，则 <改变 Y> 会使 bug 消失 / <改变 Z> 会使它更糟。」

若说不出预测，该假设只是感觉：丢弃或 sharpen。

**在测试前把排序列表展示给用户。** 他们常有领域知识能瞬间重排（「我们刚部署了改到 #3」），或知道已被排除的假设。便宜检查点，省大量时间。不要阻塞：用户不在时按你的排序继续。

## Phase 4: 埋点（Instrument）

每个探针必须映射到 Phase 3 的某条具体预测。**一次只改一个变量。**

工具偏好：

1. **Debugger / REPL 检查**（若环境支持）。一个断点胜过十条日志。
2. **针对性日志**：落在能区分假设的边界上。
3. 绝不「全打日志再 grep」。

**给每条 debug 日志打唯一前缀**，例如 `[DEBUG-a4f2]`。收尾时一次 grep 即可清理。未打标的日志会留下来；打标的会死掉。

**性能分支。** 对性能回退，日志通常是错工具。改为：先建立基线测量（timing harness、`performance.now()`、profiler、query plan），再二分。先测量，后修复。

## Phase 5: 修复 + 回归测试

在修复**之前**写回归测试，但仅当存在**正确的 seam**。

正确的 seam 是：测试在调用点处行使**真实 bug 模式**。若唯一可用的 seam 太浅（单调用方测试，而 bug 需要多调用方；unit 测试无法复现触发链），那里的回归测试只会给虚假信心。

**若没有正确的 seam，这本身就是发现。** 记下来。代码库架构在阻止把 bug 锁死。标给下一阶段。

若存在正确的 seam：

1. 把最小化复现变成该 seam 上的失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 对着原始（未最小化）场景重跑 Phase 1 反馈循环。

## Phase 6: 清理

宣告完成前必须：

- [ ] 原始复现不再复现（重跑 Phase 1 循环）
- [ ] 回归测试通过（或已记录缺少 seam）
- [ ] 所有 `[DEBUG-...]` 埋点已移除（`grep` 前缀）
- [ ] 一次性原型已删除（或移到明确标注的 debug 位置）
- [ ] 最终正确的假设已写进 commit / PR 说明，便于下次调试者学习

## 可选 HITL 清单（最后手段）

当反馈循环必须有人点击时，用结构化步骤驱动对方，而不是口头零散指挥。Agent 负责编排；人只做他们能做的动作。

对每一步：

1. 给出一条清晰指令（例如：「打开 http://localhost:3000 并登录。」）。
2. 等人确认完成。
3. 提出一个可捕获的问题（例如：「点 Export。是否报错？(y/n)」；「粘贴错误信息（或 none）：」）。
4. 把回答记为 `KEY=VALUE`，供后续假设与埋点使用。

原则：让人执行登录与点击；让 Agent 解析捕获到的观察。不要让凭证进入聊天：登录步骤用「完成即回」的确认，而不是把密码贴出来。

可选模板：`./scripts/hitl-loop.template.sh`（通用 bash，可复制后编辑步骤）。任何能运行 shell 的 Agent 都可用；不是某一产品专属。
