# Logic Prototype

一个自包含的单文件 HTML（**可分享 demo**），让任何人通过点按钮驱动状态模型。当问题关乎 **业务逻辑、状态迁移或数据形状** 时使用：那种纸面上看起来合理、但一推过真实案例就觉得不对的东西。

因为是单文件、无需安装，你可以把它交给非开发者（设计师、PM、领域专家），让他们亲手感受模型。因此它说的是他们的语言，而不是代码的语言。

## 何时是正确形状

- 「不确定这台状态机是否处理 X 然后 Y 的边角。」
- 「这个数据模型是否真能表示……的情况。」
- 「想在写之前摸清 API 应长什么样。」
- 任何有人想**按按钮并看着状态变化**的场合。

若问题是「这应该长什么样」，这是错误分支。用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

写代码之前，写下你在原型化的状态模型与问题。一段话，放在 demo 顶部（可见的 intro，不只是注释）。答错问题的 logic matt-prototype 纯属浪费，所以把问题写清楚，便于事后核对，无论用户正在看还是 AFK 回来看。

### 2. 把逻辑隔离进可移植 module

把真正在回答问题的逻辑放进单个 `<script>` 块，写成小的、纯的 module，之后可以抬出并丢进真实代码库。周围的页面是一次性的；这个 module 不是。

正确形状取决于问题：

- **纯 reducer**：`(state, action) => state`。适合动作是离散事件、状态是单一值。
- **状态机**：显式状态与迁移。适合「此刻哪些动作甚至合法」本身就是问题的一部分。
- **一小套纯函数**作用于普通数据类型。适合没有隐式当前状态、只有变换。
- **带清晰方法表面的 class 或 module**，当逻辑确实拥有持续的内部状态时。

选最贴合所问问题的形状，*不是*最容易接到页面上的形状。保持纯：无 DOM、无 `document`、无深入内部的按钮 handler。页面调用它；没有反向流动。这使 matt-prototype 在自身寿命之后仍有用：问题一答完，已验证的 reducer / machine / 函数集就能自己抬进真实 module。

### 3. 构建可分享 HTML 文件

一个文件，纯 HTML/CSS/JS：无框架、无 bundler、无 server，全部内联，双击即可打开，也能经得起邮件传来传去。任何人打开就能跑。

写给非开发者。每个标签都是 **领域语言**，不是代码：按钮与状态读起来像业务，不像 reducer。用白话解释正在发生什么。

自上而下的干净层级：

1. **标题与一行说明**：本 demo 让你探索什么（step 1 的问题）。
2. **当前状态**：完整相关状态，渲染成可读面板（带标签字段，不是生 JSON dump），每次点击后重渲染，使变化可见。在有助于非开发者跟上时，标出刚变了什么。
3. **自由试玩按钮**：每个动作一个按钮，始终可用，使任何人能以任意顺序戳模型。每次点击分发其 action 并重渲染状态。
4. **引导 walkthrough**：一组 **scenarios**，每个一页签。每个页签有一段白话描述（它建立的情境与该看什么），下方是该 scenario 的有序**按钮序列**。每一步是真按钮：点它执行该动作并进入下一步。开始 walkthrough 时重置到已知初始状态，使 scenario 每次以同样方式跑。

选择展示尴尬案例的 scenarios：纸面上难推理的那些：happy path、棘手边角、试图做本应非法的事。

保持美观但克制：干净排版、充裕留白、一个强调色。无动画、无噱头：没有任何东西与状态和按钮抢注意力。

### 4. 交接

把文件发给他们，或替他们打开。他们会在有空时点完 walkthrough 与自由试玩；有趣的时刻是他们说「等等，那不该可能」或「咦，我以为 X 会不一样」；那些是*想法*里的 bug，正是全部意义所在。若他们要新动作或新 scenario，加上去。Prototype 会演化。

### 5. 捕获答案与 matt-prototype

一旦 matt-prototype 回答了问题，先捕获答案，再按 [SKILL](SKILL.md) 描述的方式捕获 matt-prototype。Logic 特有的映射：已验证的 reducer / machine / 函数集抬进真实 module（被吸收的决策）；HTML 壳跟着到保留 matt-prototype 作为 primary source 的一次性分支；作为自包含单文件，它在那里仍 trivial 可重跑。

## 反模式

- **不要加测试。** 需要测试的 matt-prototype 就不再是 matt-prototype。
- **不要接到真实数据库。** 除非问题明确关于持久化，否则用内存状态。
- **不要泛化。** 没有「万一以后要支持 X」。Prototype 只答一个问题。
- **不要把逻辑与页面糊在一起。** 若纯 module 引用 DOM、`document` 或按钮 handler，它就不再可抬。让页面做纯 module 上的薄壳。
- **不要伸手要框架、bundler 或 server。** 接收者双击一个文件即可；React 应用或 dev server 会毁掉「可分享」。
- **不要把 HTML 壳送进生产。** 页面为被人手工点过而优化。背后的逻辑 module 才是值得保留的部分。
