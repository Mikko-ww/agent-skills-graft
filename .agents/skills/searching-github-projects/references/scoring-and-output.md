# 评分与输出规范

在候选较多、需要分级或比较质量时读取本文件。

## 三维评分

不要用单个“总分”隐藏项目差异。先独立打分，再按用户目标排序。

### 相似度（0–100）

| 维度 | 权重 | 判断问题 |
|---|---:|---|
| 产品形态 | 25 | 同为完整产品、工作台、SDK、CLI、插件或模型吗？ |
| 核心工作流 | 25 | 用户完成任务的步骤是否接近？ |
| 核心能力 | 25 | 必须具备的能力覆盖多少？ |
| 目标用户/场景 | 15 | 服务的人群和使用场景是否相同？ |
| 部署与交付 | 10 | SaaS、自托管、桌面端、API 等是否接近？ |

锚点：

- 90–100：可视为直接开源替代或高度同类产品。
- 75–89：主流程相同，但交互、场景或交付方式有明显差异。
- 55–74：只覆盖部分流程，适合参考模块。
- <55：底层依赖、邻近类别或关键词误匹配。

### 适合度（0–100）

| 维度 | 权重 | 判断问题 |
|---|---:|---|
| 用户硬需求 | 35 | 必须能力和约束是否满足？ |
| 可复用价值 | 25 | 架构、代码或产品设计能否被用户采用？ |
| 技术/部署匹配 | 15 | 技术栈、平台和运维复杂度是否可接受？ |
| 许可证 | 15 | 是否符合开源、闭源或商业化计划？ |
| 成熟度匹配 | 10 | 用户要 MVP 灵感还是生产底座？ |

硬约束不满足时，即使高度相似，也不得给高适合度。

### 项目质量（0–100）

| 维度 | 权重 | 证据 |
|---|---:|---|
| 同类采用度 | 20 | Star/Fork 在同类项目中的相对位置 |
| 维护活跃度 | 20 | 近期提交、Issue/PR 响应、Release |
| 文档与可运行性 | 15 | 安装、部署、架构、示例是否完整 |
| 工程质量 | 15 | 测试、CI、版本管理、错误处理 |
| 社区健康度 | 10 | 贡献者分布、治理、讨论与用户反馈 |
| 许可证与透明度 | 10 | LICENSE、开源边界、依赖是否清楚 |
| Star 趋势 | 10 | 可验证的 30/90 天增长；未知时不臆测 |

Star 应在同类仓库中比较。10k Star 的论文实现不能因此成为最佳产品对标；500 Star 的直接替代品可能比 100k Star 的底层框架更值得优先研究。

若 Star 趋势无法核验，把该项标为未知，并根据其余证据给出区间或降低置信度。

## 综合排序

默认综合参考：

```text
综合参考价值 = 相似度 × 45% + 适合度 × 35% + 项目质量 × 20%
```

这个数只用于辅助排序，用户可见结果仍展示三个维度。用户明确要求“用于生产”时提高适合度/质量权重；明确要求“找最像的竞品”时提高相似度权重。

## 分级

| 分级 | 分数 | 含义 |
|---|---:|---|
| A | 85–100 | 高度匹配，优先深入研究 |
| B | 70–84 | 强参考，需补齐部分能力 |
| C | 55–69 | 模块级或邻近参考 |
| D | <55 | 通常排除；必要时解释误匹配原因 |

分级通常以综合参考价值为主，同时允许基于硬约束降级。说明降级原因。

## 可疑高热度信号

高 Star 项目出现以下情况时，不直接判定低质量，但需要进一步核验并提示风险：

- 创建时间很短、Star 激增，却几乎没有 Fork、Issue、贡献者或 Release。
- README 营销内容很多，安装、代码结构、许可证或运行方式不清楚。
- 核心能力仅存在于托管云服务，开源仓库只是 SDK、入口页或演示。
- 提交集中来自极少数账号，Issue/PR 长期无人响应。
- 仓库名、描述或 Topics 大量堆砌热门关键词。
- 默认分支代码与 README 展示的产品不一致。

不要把“项目较新”本身作为否定证据；报告成熟度和验证边界即可。

## 推荐输出模板

```markdown
我将你的需求理解为：[用户目的]。这里的 [产品/名词] 指 [消歧结论与产品指纹]，
因此重点搜索 [类别/形态/工作流]，排除 [不相关类别]。

## A 级：优先研究

### [owner/repo](URL) — 12.4k Stars
- 简介：[一句话说明它是什么]
- 分级：A
- 相似度：92/100
- 适合度：88/100
- 项目质量：84/100
- 近期 Star 趋势：近 30 天 +820（来源，日期）/ 未核验
- 推荐理由：[与用户目标直接对应]
- 注意事项：[许可证、成熟度、部署、开源边界]

## B 级：强模块参考
[同样字段]

## 优先阅读顺序
1. [仓库]：重点看 [产品/模块]
2. [仓库]：重点看 [工作流/模块]
3. [仓库]：重点看 [基础设施/模块]

## 数据说明
- 当前 Star：GitHub，获取于 YYYY-MM-DD
- Star 趋势：[来源与窗口，或“未核验”]
- 分数：根据公开 README、仓库元数据和用户约束近似评估
```

## 意图不清时的输出

不要先给一大批仓库。先说明为什么选择会分叉，然后问一个问题：

```markdown
“Agent memory”可能指通用记忆 API、知识图谱记忆、编程 Agent 本地记忆，
或完整的有状态 Agent Runtime；这几类的最佳项目不同。

你更想做哪一种？
1. 通用 Memory API（推荐）
2. 编程 Agent 记忆
3. 企业知识/图谱记忆
4. 完整 Agent Runtime
```

用户回答后再检索。若用户明确允许“先给概览”，可以分赛道给少量代表项，但仍要标明类别差异。
