# Searching GitHub Projects

## 核心原则

搜索用户真正要解决的问题，而不是机械复用用户输入的词。先建立目标产品或方向的准确画像，再多路发现候选、核验实时证据，最后分别评价相似度、适合度和项目质量。

星数是采用度信号，不等于相似度或代码质量。`updatedAt`、最近提交和发布时间也不等于 Star 趋势。

## 快速决策

1. 用户提到具体产品、项目或陌生名词：先执行“实体消歧”。
2. 用户已说明目的、约束和参考维度：直接检索，并明确你的理解。
3. 不同理解会显著改变结果：只问一个最关键的澄清问题。
4. 信息虽不完整但存在合理默认值：说明假设后继续，不要制造不必要的问答。

以下条件同时成立时，先澄清，不要先搜索或输出排行榜：

- 用户只给出宽泛方向，例如 `Agent memory`、RAG、AI workflow、observability。
- 用户说要“做产品/找项目”，但没有目标用户、核心场景、产品形态或必须能力。
- 该方向至少包含三个明显不同的产品赛道，选择不同赛道会改变首选仓库。

此时回答的形状是：一句话解释赛道为何分叉，然后只问一个带 2–4 个选项的问题。不要一边假设默认赛道，一边继续给项目列表。

常见关键问题：

- “你主要想直接使用、二次开发，还是研究它来做类似产品？”
- “你说的相似，是界面形态、业务工作流，还是底层技术能力？”
- “必须自托管和可商用吗？”

例如用户只说“想做 Agent memory 产品”时，先让其在“通用 Memory API、编程 Agent 记忆、企业知识/图谱记忆、完整 Agent Runtime”中选择；这些赛道的高质量项目并不相同。

提供 2–4 个具体选项，并把推荐选项放在第一位。

## 工作流

### 1. 理解真实需求

从请求中提取：

- **行动目的**：直接使用、技术选型、二次开发、竞品研究、学习架构或自研产品。
- **目标对象**：产品类别、目标用户和典型使用场景。
- **核心能力**：没有这些能力就不应进入首选。
- **产品形态**：Web、桌面、CLI、SDK、Agent、工作流、画布或底层模型。
- **约束**：语言、技术栈、自托管、许可证、部署方式、维护成本。
- **质量偏好**：高 Star、近期增长、成熟稳定、活跃开发或企业采用。
- **排除项**：论文实现、资源合集、Demo、SDK、底层模型等是否与目标不符。

用户说“类似 X”时，不能仅搜索 X 的名字。

### 2. 实体消歧与产品画像

先搜索该名词或产品的准确含义。优先证据：

1. 官方网站、官方文档、官方 GitHub 组织与 README。
2. 可信的产品介绍、发布公告或维护者说明。
3. 第三方文章只用于补充，不用来覆盖官方定义。

确认：

- 名称是否存在重名或缩写碰撞。
- 用户指的是产品本体、开源仓库、API、插件还是生态项目。
- 产品的目标用户、核心工作流、交互形态、关键能力和部署模式。

形成一句“产品指纹”，例如：

> LibTV = 面向 AI 视频创作者的画布式工作台，覆盖剧本/分镜、图像与视频生成、素材编排，并可被 Agent/API 调用。

后续检索必须围绕产品指纹展开。无法可靠确认实体时，向用户展示冲突的解释并请其选择。

### 3. 生成搜索简报

在内部整理：

```text
目标：
参考实体及产品指纹：
必须具备：
最好具备：
排除：
用户约束：
质量偏好：
```

如果无法填写“目标”或“必须具备”，且不同答案会改变推荐，先澄清。

### 4. 多路发现候选

至少覆盖三类查询，不依赖单个关键词：

- **实体与生态**：产品名、官方组织、替代品、竞品、集成和 Fork。
- **产品形态**：如 `infinite canvas`、`AI video workspace`、`code review agent`。
- **核心工作流**：如 `script to storyboard to video`、`webhook pull request review`。
- **技术能力**：如 MCP、GitHub App、self-hosted、multi-provider。
- **GitHub Topics 与中英文同义词**。

先宽搜发现词汇，再用高价值词收窄。对每条查询记录它覆盖的意图维度。具体命令和查询策略见 [search-strategy.md](references/search-strategy.md)。

### 5. 核验候选

对计划推荐的仓库逐个打开仓库元数据和 README，不根据搜索摘要直接排名。

必须核验：

- 仓库链接、简介、当前 Star 数和数据获取日期。
- 是否归档、是否只是 Fork、主要语言、许可证。
- 产品形态和核心能力是否真的匹配。
- 最近提交、Release、Issue/PR、贡献者与文档状况。
- 用户准备二次开发时，检查部署方式、配置复杂度、测试/CI 和许可证风险。

近期 Star 趋势只有在获得可靠时间序列时才报告，并注明窗口与来源，例如 `近 30 天 +1,240`。可以使用 GitHub stargazer 时间数据、Star History 或可信的 OSS 分析服务。

没有可靠趋势数据时写“近期 Star 趋势：未核验”。不得用仓库更新时间、总 Star 或主观感觉代替趋势。

### 6. 分开评分再排序

使用三个独立维度：

- **相似度**：产品形态、核心工作流、核心能力、目标用户、部署模式与参考对象的接近程度。
- **适合度**：满足用户目的和硬约束、可复用架构、技术栈、许可证及落地成本。
- **项目质量**：同类采用度、维护活跃度、文档、发布与测试、贡献者健康度、许可证治理和可验证的 Star 趋势。

综合排序建议：相似度 45%、适合度 35%、项目质量 20%。如果用户明确强调某一维度，调整权重并说明。

分级：

- **A / 85–100**：高度匹配，应优先深入研究。
- **B / 70–84**：较强参考，部分模块或形态存在差异。
- **C / 55–69**：局部有价值，不适合作为主要对标。
- **D / <55**：通常不进入推荐列表；必要时作为“为什么不选”的反例。

评分是基于可见证据的近似判断，不要伪装成客观测量。完整评分锚点见 [scoring-and-output.md](references/scoring-and-output.md)。

### 7. 输出结果

先用 1–3 句话说明：

- 你如何理解用户真实需求。
- 对具体名词/产品的消歧结果。
- 搜索结果中需要注意的类别差异。

按 A、B、C 级组织候选。每个仓库必须包含：

```markdown
### [owner/repo](GitHub URL) — 12.4k Stars
- 简介：
- 分级：A
- 相似度：92/100
- 适合度：88/100
- 项目质量：84/100
- 近期 Star 趋势：近 30 天 +820（来源）/ 未核验
- 推荐理由：
- 注意事项：许可证、成熟度、部署或范围差异
```

最后给出：

- **优先阅读顺序**：通常 3 个以内，并说明各自负责哪部分参考。
- **组合建议**：产品层、工作流层、Agent 层、基础设施层如何取长补短。
- **数据说明**：Star 获取日期、趋势来源和未核验项。

结果较少时可压缩格式，但链接、当前 Star、简介、分级和推荐理由不可省略。

## 质量护栏

- 不把“高星但类型不同”的项目排在高度相似项目前面。
- 不把论文、模型、SDK、Awesome List 或底层引擎描述成完整产品。
- 不引用记忆中的 Star 数；实时核验后再写。
- 不因为描述中命中关键词就断言具备某项功能；README 或代码必须支持判断。
- 不把近期提交、创建时间或 Release 数量称作 Star 趋势。
- 不隐瞒许可证、归档、项目过新、缺少源码或核心功能仅在云端等限制。
- 不用过度精确的综合分掩盖证据不足；无法判断时明确标注。

## 示例

用户：“我想做一个类似 LibTV 的工具，希望找到相似度高且高星的项目。”

正确处理：

1. 先确认 LibTV 指向哪个产品，并从官方资料提取产品指纹。
2. 判断用户目的为“自研产品参考”，而不是寻找底层文生视频模型。
3. 分别搜索无限画布、AI 视频工作台、剧本到分镜/视频、Agent/API 调用层。
4. 将相似产品放 A 级；将高星短剧流水线放 B 级；将 ComfyUI、视频模型和画布 SDK 放 C 级或基础设施参考。
5. 当前 Star 实时核验；趋势无法取到就写“未核验”。

错误处理：只搜 `LibTV` 或 `text-to-video`，然后按 Star 从高到低列出结果。
